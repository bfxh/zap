# zap —— 能装在手机和电脑上的多线程 PPMd 压缩器

纯 Rust，零第三方运行时依赖，单文件可执行。**1GB 文件 64 秒压完**（2 线程，15.5 MB/s，1.6316 bit/byte）；
换 `ZAP_LEVEL=max` 是 1.5107（188.8MB），2 分钟——同一个工具里从 24 MB/s 到 8.6 MB/s 三档可选。

    zap c <in> <out> [threads]     压缩
    zap d <in> <out> [threads]     解压
    zap t <in> [threads]           自检（压缩 + 解压 + 逐字节比对）

不给 `threads` 就用满所有核。

## 为什么不是 CM

上下文混合（CM）能压到 1.4203 bit/byte，但单核只有 0.28 MB/s，1GB 要 59 分钟——手机上等于不能用。
CM 每字节约 100 次随机内存访存，天生重。
zap 换回 PPMd（单线程已有 9 MB/s 量级），再把输入切块并行，速度随核数上升，
代价是每块都要重新学模型。

## 三档：按用途选，不用记参数

    ZAP_LEVEL=fast zap c 大文件.zap                最快，手机上也不难受
    zap c 大文件 大文件.zap                        默认 std
    ZAP_LEVEL=max zap c 大文件 大文件.zap          最小，吃内存

| 档 | 阶数 | 每线程内存 | 块 | 1GB enwik9 输出 | bit/byte | 速度 |
|---|---|---|---|---|---|---|
| `fast` | 5 | **24MB** | 8MB | 219,647,108 | 1.7572 | 24.7 MB/s（40.5s） |
| `std`（默认） | 6 | **96MB** | 32MB | **203,952,532** | **1.6316** | 15.54 MB/s |
| `max` | 8 | 512MB | 128MB | **188,840,231** | **1.5107** | 8.57 MB/s |

### 内存阶梯：哪里能省，哪里省了就掉体积

模型池（`ZAP_MEM`，每线程）不是越大越好——超过实际用量就是白占内存，低于用量就开始丢精度。
1GB / 2 线程实测，同一个档位只改池大小：

| 档 | 池 | 输出 | 相对该档原文 |
|---|---|---|---|
| `fast`（8MB 块） | 32MB | 219,647,108 | v0.3.1 默认 |
| | **24MB（现在默认）** | **219,647,108** | **逐字节相同，白省 8MB，速度不变** |
| | 20MB | 219,709,137 | +0.03% |
| | 16MB（可选，`ZAP_MEM=16`） | 222,865,544 | +1.47%，但压/解快 6.6% / 4%，手机内存再减 1/3 |
| | 12MB | 224,664,620 | +2.29%，再快 14% |
| `std`（32MB 块） | 128MB | 203,952,532 | v0.3.1 默认 |
| | **96MB（现在默认）** | **203,952,532** | **逐字节相同，白省 32MB，速度不变** |
| | 64MB | 207,160,298 | +1.57% |

所以默认值都改到了**不损失一个字节的最低点**：`fast` 32→24MB、`std` 128→96MB，产出与 v0.3.1 逐字节一致。
想再快一点就自己往下拧：`ZAP_MEM=16`（fast）用 1.47% 体积换 6.6% 速度；不想要这个取舍，默认值本来就不掉体积。


单看压缩率先看块大小——块越大，每块"从零学模型"的次数越少：

| 块大小（o6，2 线程） | 输出 | bit/byte | 速度 |
|---|---|---|---|
| 8MB / 32MB | 211,917,036 | 1.6953 | 17.19 MB/s |
| 32MB / 128–256MB | 203,952,532 | 1.6316 | 15.54 MB/s |
| 64MB / 256MB | 200,803,648 | 1.6064 | 14.12 MB/s |
| 128MB / 256MB | 198,483,914 | 1.5879 | 12.32 MB/s |
| 不切块，1 线程单流 | 197,118,093 | 1.5769 | 6.25 MB/s |

最后一行是天花板：**再大的块也追不平"一个流到底"**，但也没必要——128MB 已经贴到 0.7% 以内。

## 剩下的旋钮

| 环境变量 | 默认 | 含义 |
|---|---|---|
| `ZAP_LEVEL` | std | `fast` / `std` / `max`，决定下面三个的默认值 |
| `ZAP_ORDER` | 6 | PPMd 阶数。8 更小（约 −4%），但慢 1.5 倍 |
| `ZAP_MEM` | 见档位 | **每线程**模型内存 MB。32MB 块 96MB 就够（128MB 与 96MB 产出逐字节相同）；8MB 块 24MB 就够（默认），再降到 16MB 用 1.5% 体积换 6.6% 速度 |
| `ZAP_BSZ` | 预设块大小 | 块大小 MB，`0` = 自动（总长 /（线程×2），夹在 4–32） |

## 试过但没采用：块间预热

想法很自然：让每块的模型先"读"一段公共前缀，别从零学起。
做法是把文件开头 S 字节先编码一次，码流只存流头一份，各块解码时接在同一状态后面（无损、块间仍独立）。

16MB 切片（o6 / 4MB 块 / 2 线程）逐档实测，基线 4,123,813 字节：

| 预热样本 | 输出 | 相对无预热 |
|---|---|---|
| 0 | 4,123,813 | — |
| 64KB | 4,119,835 | **−0.10%** |
| 128KB | 4,121,309 | −0.06% |
| 256KB | 4,122,981 | −0.02% |
| 512KB | 4,142,309 | +0.45% |
| 1MB | 4,195,097 | +1.7% |

1GB enwik9（o6 / 32MB 块 / 2 线程）上，最多只到 64KB 这一档：203,843,893，**−0.05%**。
**PPMd 的模型是"见过就强烈押注"的类型**，喂一大段别人的文本会把概率推进到过度自信，
自己那块反而编码更贵。收益最大只有 0.05%，抵不上多一个格式版本，所以没进主线
（实现留在 git 历史里，`ZAP_SAMPLE` 环境变量那版）。
真正吃这块损失的办法是"整段一个流"，也就是上表最后一行——但那要牺牲并行。

## 试过但没采用：预取与本地化

PPMd 的时间几乎都花在随机访存上，所以先怀疑缓存。三个候选都在真机上做过 A/B
（同一台机器交替跑 5–6 轮取中位数；每次都是 16MB 文本、单线程、o6 / 128MB / 32MB 块）：

| 改法 | 相对基线 | 结论 |
|---|---|---|
| 解码入口预取下一层 suffix 记录 | 0%（−4.5% ~ +4.4% 之间抖） | 85% 的符号用不到它，纯属浪费 |
| `-C target-cpu=native`（AVX2/BMI2） | **−2.5%**（更慢） | SIMD 本来就在运行时派发，代码生成没有红利 |
| `opt-level=2` | 无差异 | 不是代码密度的问题 |
| Linux PGO（`-Cprofile-use`） | ≈0（噪声内） | 同上 |

真正有效的是**把 arena 调小**：同样 16MB 文本，32MB arena 比 128MB 快 **18%**，
代价是体积从 1.8726 涨到 1.9339 bit/byte。也就是说瓶颈是"随机访存塞不进缓存"，
不是指令条数——而 arena 大小已经是现成的旋钮：`ZAP_LEVEL=fast` 走的就是这条路（1.5× 速度换 7.7% 体积）。
真正想用密度化把剩下的部分拿回来，也被数据否了：微基准里把 6 字节状态换成 2 字节的符号+频率
（后继另放 4 字节），冷扫描（128MB 随机）只快 **1.28×**，热扫描（1MB 常驻）是 **1.01×**。
PPMd 的上下文重用性很强，多数扫描本来就是热的，按命中率加权整体只有 3–5%。

callgrind 也给出了同样的方向：1MB 输入里 `update_model` 占 24.8%、`create_successors` 占 11.2%，
真正花在扫描状态数组上的只是一部分；16MB 切片 D1 miss 4,851 万（读 miss 率 4.0%）、LL miss 122 万。
也就是说密度化最多动到"扫描"这半边，另一半（更新）它碰不到。

更关键的是它和 PPMd 的更新方式直接冲突：现在 6 字节一个槽、两块一页，
一个上下文有奇数个状态时正好余 6 字节空位，所以"学到一个新符号就原地加一条"是一次写入；
拆成符号 / 频率 / 后继三段数组后，再加一条就得把频率段和后继段整体后移，
而这件事**每个符号、每一层后缀上下文都要做一次**——每符号几百字节 memmove，
正好把省下的扫描时间吃回去，还有可能更慢。

最后还有格式账：保住重启点不变（=旧归档还能解）就得让每线程内存翻倍，
不然只能改重启点、再升一个格式版本。三条加起来，不值。
## v0.1 → v0.2 改了什么

两处结构性浪费，都不影响压缩率（压缩出来的**每个块逐字节不变**）：

| 项 | v0.1 | v0.2 | 变化 |
|---|---|---|---|
| 压缩 1GB（o6/32MB/256MB/2 线程） | 67.0s，14.92 MB/s | **63.6s，15.72 MB/s** | +5.4% |
| 压缩峰值 RSS | 422MB | **254MB** | −40% |
| 解压 1GB | 72.1s，13.86 MB/s | **68.6s，14.57 MB/s** | +5.2% |
| 解压峰值 RSS | 1124MB | **254MB** | −77% |
| 归档体积 | 203,952,292 | 203,952,532 | +240 字节 |

- **模型复用**：每个线程只 `new` 一次 encoder，块与块之间 `reset` 复用同一份模型存储，
  不再"压一块就申请 256MB、压完再还回去"。
- **结果直落盘**：压缩时按原子游标申请偏移、直接写进最终文件；解压同理按块偏移写。
  内存里只留索引，不再把整包压缩数据（或整份输出）攒在 `Vec` 里——解压峰值从 1.1GB 降到 254MB。
- 代价是索引从 8 字节变成 16 字节（多一个 u64 偏移），30 块多 240 字节，0.0001%。
- 码流格式随之升到 **ZAP2**；v0.1 的 ZAP1 归档仍能解码（`decodes_v1_archive` 用例 + 1GB 实测都验过）。

## v0.3.1 → v0.3.2 改了什么

只动两行默认值，格式、码流路径、代码逻辑都没变（旧归档照旧能解）：

| 项 | v0.3.1 | v0.3.2 |
|---|---|---|
| `fast` 每线程池 | 32MB | **24MB**（1GB 输出 219,647,108 逐字节相同，内存 −25%，速度不变；`ZAP_MEM=16` 可再换 6.6% 速度） |
| `std` 每线程池 | 128MB | **96MB**（1GB 输出 203,952,532 逐字节相同，内存 −25%，速度不变） |

理由是实测出来的"内存阶梯"：32MB 块实际吃不到 96MB，8MB 块吃不到 24MB，多给的部分从来没被用上。
想要 v0.3.1 的体积，`ZAP_MEM=24`（fast）/ `ZAP_MEM=128`（std）就回去了。

## v0.2 → v0.3 改了什么

只加了一层"按用途选档"，**码流格式没动**（还是 ZAP2，阶数和内存本来就记在文件头里，
所以三档压出来的归档互相都能解）。变化是把默认值调到实测最划算的位置：
块大小 32MB、每线程 128MB——128MB 再往上给内存，体积一个字节都不变（32MB 块吃不满）。

## 线程不是越多越好

Windows，24 核 / 15GB，输入是一份 505MB 的已压缩安装包（8.12 bit/byte，压不动，纯测速度）：

| 线程 | 1 | 2 | 4 | 8 | 12 | 24 |
|---|---|---|---|---|---|---|
| MB/s | 4.41 | 7.54 | 12.27 | 19.03 | 22.04 | 20.11 |

拐点在 8–12 线程：PPMd 是随机访存密集的，线程再多就被内存带宽吃掉。
**电脑建议 8 线程，手机 4 线程**，不要"有多少核开多少"。解压后 SHA256 与原文件一致。

## C 接口（给手机 App / 别的语言）

三个函数，全部是**单块**语义，`order` 与 `mem_mb` 压解必须一致：

    int  zap_compress_buf(const uint8_t* data, size_t len, uint32_t order, uint32_t mem_mb,
                          uint8_t** out_ptr, size_t* out_len);
    int  zap_decompress_buf(const uint8_t* data, size_t len, size_t unpacked_len,
                            uint32_t order, uint32_t mem_mb,
                            uint8_t** out_ptr, size_t* out_len);
    void zap_free(uint8_t* ptr, size_t len);

返回 0 成功，1 参数非法，2 编码/解码失败，3 内部 panic（已 `catch_unwind`，不会炸调用方进程）。
输出的缓冲区用 `zap_free(ptr, len)` 释放，`len` 必须用返回值。
`test_zap.c` 是最小示例（55 字节文本 → 20 字节 → 原样还原）。

## 文件格式

ZAP2（当前）：

    "ZAP2" | nblocks u32 | total u64 | order u8 | mem_mb u16      # 19 字节
    每块：blen u32 | clen u32 | off u64                             # 16 字节 × nblocks
    各块的 PPMd 流，按 off 定位（写入顺序＝完成顺序，与块序无关）

ZAP1（v0.1，仍可解码）：目录项只有 `blen u32 | clen u32`，流按块序隐式拼接。

参数全在头部，解码只读流、不看环境变量（早期丢过参数、导致 1GB 解码在第 12 字节分叉）。
单块长度用 u32，因此块必须小于 4GB——分块设计本身已经保证了这点。

## 已知取舍

- 分块并行 = 每块重新学模型：4MB 块比整块大约 5%，8MB 约 2.5%，16MB 约 1%。
- 单块内 PPMd 仍是单线程；想再快就减块或降阶（o4 约快 1.5 倍、损 3%）。
- `ZAP_MEM` 是每线程的：`fast` 4 线程 × 24MB = 96MB（降到 16MB 则 64MB），`std` 4 线程 × 96MB = 384MB，低端机按档选。
- 解压时块目录已进内存（每块 16 字节），块数据按偏移随机读、结果按偏移直写，
  既不整包载入，也不整份攒在内存里。
